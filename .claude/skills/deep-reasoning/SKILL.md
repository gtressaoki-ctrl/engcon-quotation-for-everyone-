# deep-reasoning：複雑タスクの思考手順

実装を始める前に、以下の 7 ステップを**順番に**実行する。
各ステップの成果物（文章）を作業メモまたは PR 説明に残すこと。
「明らかに簡単」に見えても、下記のトリガーに該当したらスキップ禁止。

## いつ使うか（トリガー）
- 3ファイル以上に変更が及ぶ、または新しい画面/API/テーブルを作る
- lib/pricing.ts・lib/standardConfig.ts・lib/machineCatalog.ts（価格・品番ロジック）に触る
- Supabase スキーマ・RLS・migration に触る
- 仕様が文書（docs/specs, docs/adr, README）に存在しないことを頼まれた
- 「どう実装するか」に複数のもっともらしい方法がある

## 手順

### 1. 問題の再定義
- 依頼を自分の言葉で 2〜3 文に言い換える
- 「完了」の定義を書く（誰が・何をできるようになれば完了か）
- 依頼文と docs/specs・docs/adr に矛盾がないか確認。矛盾があれば**実装せずユーザーに確認**

### 2. 制約の列挙
- 技術制約：Next.js 14 App Router / Supabase RLS / Vercel serverless / PWA
- このリポジトリの制約：.claude/rules/ と docs/adr/ の決定事項（ADR に反する変更は禁止）
- ビジネス制約：価格掛け率・品番はビジネスデータ（勝手に変更禁止、出典必須）

### 3. 複数案の比較（最低 2 案）
- 各案について：概要／メリット／デメリット／影響範囲／ロールバック容易性
- 「案が 1 つしか思いつかない」場合は、少なくとも「やらない」案と比較する

### 4. 選定と理由の記録
- 採用案と、**却下した案の却下理由**を書く
- アーキテクチャ・データモデル・価格ロジックに関わる判断なら docs/adr/ に ADR を追加
- ここで未決の判断を残さない：決められないことはユーザーに質問して決めてから進む

### 5. 検証計画（実装前に書く）
- どのテストで正しさを証明するか（追加するユニットテスト名まで書く）
- `npm run typecheck` / `npm run lint` / `npm run test` / `npm run build` が通ること
- 手動確認する画面フロー（例：/wizard で CAT 320 DC3 SW を選び STEP5 の品目を確認）

### 6. 実装
- 小さい単位で commit（1 commit = 1 論点）
- 品番・価格データを変えた場合、出典（Excel/価格表/ユーザー指示）を commit message に書く

### 7. 自己レビュー
- .claude/skills/code-review/SKILL.md のチェックリストを diff に対して実行
- 検証計画（ステップ 5）を全部実行し、結果を報告に含める
- 報告は日本語・結論先行。選択肢を提示するときは必ず理由とトレードオフ付き

## 禁止事項
- ステップ 5 の検証計画なしに実装を始めること
- テスト未通過のまま commit すること
- docs/adr の決定に反する実装（変更したい場合は ADR の改訂をユーザーに提案する）
